# 君一知识库

**“君一”是方法来源，不是分类模板。** 本 Skill 服务使用者自己的知识库，不复制君一七领域，不套历史五类人物模型，也不要求从零发明一套目录。

本 Skill 只负责知识库的**分类、文件夹搭建、重整、归档和诊断**。它不生成 `USER.md`、`CLAUDE.md`、`AGENTS.md`、工作台入口、当前主线或项目 `README.md`；这些属于后续工作台开通流程。

## 先判断模式

1. 确认唯一目标知识库根目录。路径不明确时先定位，不根据文件夹名猜测。
2. 只读扫描现有结构；可运行：

   ```bash
   python3 scripts/scan_vault.py <知识库根目录>
   ```

3. 路由到一种模式：
   - **搭建模式**：目标目录不存在或基本为空，从默认功能骨架形成第一版结构。
   - **重整／诊断模式**：已有知识库，需要判断现有分类应保留、补齐还是退出运行层。
   - **归档模式**：现有分类仍适用，只需放入一条或一批内容。
4. 状态不明确时展示扫描证据和建议模式，让使用者确认；不要用“可能是空库”直接创建。

已有 Obsidian 不等于需要新建文件夹。旧库先映射已有能力，能够沿用的就沿用；“重新整理”也不等于授权批量迁移。

## 不可违反的规则

- 任何创建目录、写入、移动、重命名、合并或覆盖之前，先展示完整计划和目标路径。
- 新增、拆分、合并或退出顶层分类必须获得本人确认；不确定时给 2–3 个候选和差异。
- 默认不覆盖现有文件。批量操作默认 dry-run；只有本人确认本次计划后才使用 `--apply`。
- 重整／诊断默认只读。结构判断、迁移计划和迁移动作分开，不能在同一步完成。
- 不删除原文，不把原话切碎，不根据标题编造正文结构。
- 现有命名是证据，不是必须保留或必须改掉的前提。
- 私密内容不因为进入知识库就自动获得公开授权。普通文件夹也不等同于真正的访问权限隔离。
- 不让符号链接、绝对路径或 `..` 路径逃出目标根目录。

## 默认能力骨架

新库从四项默认能力开始，而不是从空白访谈开始：

1. **事业／工作与项目**：正在推进的工作、业务和项目上下文；
2. **个人与生活**：个人成长、生活责任及尚未需要独立成域的家庭、健康等内容；
3. **知识与资产**：学习输入，以及跨项目反复使用的判断、方法、案例、语料、模板和 Skill；
4. **收件箱**：尚未判断去向的临时入口，必须有清理规则。

它们是默认能力，不是四个永远固定的名称。搭建时只做**改名、合并、拆分或最多新增两个顶层领域**，通常形成 3–6 个顶层文件夹。某项内容只有在“高频产生／检索、长期独立责任、明显检索或隐私边界”三项中满足至少两项，才升为顶层领域。

## 搭建模式

读取 [build-mode.md](references/build-mode.md) 并执行：

1. 问 2 个必答问题和 1 个隐私选答；不要展开九项经营访谈。
2. 用本人最近真实处理的 3 份材料或任务测试默认骨架。
3. 只在真实材料放不下时调整，输出 3–6 个顶层文件夹及必要的最小子目录。
4. 展示每个目录“收什么／不收什么”、三条真实归档路径和暂不建立的分类。
5. 本人确认后生成操作 manifest，先 dry-run：

   ```bash
   python3 scripts/apply_manifest.py plan.json --root <目标目录>
   ```

6. 本人再次明确确认后再执行：

   ```bash
   python3 scripts/apply_manifest.py plan.json --root <目标目录> --apply
   ```

7. 重新扫描，确认只创建了已确认目录，没有生成后续工作台文件或覆盖原文件。

## 重整／诊断模式

读取 [audit-mode.md](references/audit-mode.md) 并执行：

1. 把现有顶层目录映射到四项默认能力，先找“已具备”，再找重复和缺口。
2. 用同样的 2 个必答问题、1 个隐私选答和 3 个真实材料测试校准，不重做长访谈。
3. 输出保留、改名候选、合并候选、迁入历史候选、新增候选、待观察和不能自动处理。
4. 先给新旧映射、风险、迁移批次和回滚点；本人确认前不生成 apply manifest。
5. 每批迁移单独预览、确认、执行和验收，不一次性大搬家。

## 归档模式

读取 [file-mode.md](references/file-mode.md) 和 [schema-decision.md](references/schema-decision.md)：

1. 扫描现有领域、类别和命名约定。
2. 判断内容未来最可能为什么任务被找回来，再选择位置；主题相似但用途不同的内容不强行放一起。
3. 给出置信度与依据。低置信度必须询问；现有分类都不合适时提出最小新增方案并等待确认。
4. 展示目标路径、文件名、frontmatter、内容结构和冲突处理方式。
5. 确认后通过 manifest 写入；覆盖必须单独明确授权。

## 完成验收与交接

- `scan_vault.py` 的结果与已确认计划一致；
- 顶层文件夹通常为 3–6 个，每一个都能回答“什么任务会再次来找它”；
- 三份真实材料都有一个本人认可的首选位置；
- manifest 中每个路径都在根目录内，没有未说明冲突；
- 新文件可用 UTF-8 读取、无 U+FFFD，frontmatter 合法；
- 没有覆盖、删除或移动计划之外的文件；
- 未生成 `USER.md`、`CLAUDE.md`、`AGENTS.md`、工作台入口、当前主线或项目 `README.md`。

需要继续开通个人 AI 工作台时，只交接：已确认的目录结构、每个目录的边界、三份材料的归档示例、隐私限制和仍待确认项。不要重复运行已经完成的分类访谈。
