## 事实与来源

档案中的内容必须属于以下一种来源：

| 来源 | 可以做什么 | 例子 |
|---|---|---|
| `user_fact` | 写入用户明确陈述的事实、感受、需求和承诺 | “她是我的客户” |
| `system_computed` | 换算日期、生成 ID、规范状态值 | “下周三”换算为 `2026-07-29` |
| `system_suggestion` | 在回执中提出建议，不直接写成关系事实 | “这段关系可能进入熟悉阶段” |

“100% 基于原话”指不得发明人物背景、关系质量、需求、紧迫度、资源、感受或动机。允许生成忠实的结构化摘要，但必须同时保留用户原始表达并标注摘要是系统提取。

缺失值统一处理：

- 文本字段：`待确认`
- 数字字段：`null`
- 状态字段：`unknown`
- 日期字段：`null`

不得用“外圈”“亲密度 2”“熟悉”等看似合理的值替代缺失信息。

## 身份与同名消歧

### 唯一标识

每个人必须有稳定 `person_id`：

```text
person_YYYYMMDD_8位小写字母数字
```

例如：

```text
person_20260724_ab12cd34
```

生成 ID 属于 `system_computed`，不代表用户事实。ID 一旦写入不得因改名、身份变化或文件移动而改变。

文件名格式：

```text
姓名--身份标识--ID后8位.md
```

身份标识只能取自用户明确提供的稳定线索，例如“瑜伽老师”“企业法务客户”“做居家照护产品”。可以做不增加含义的最小压缩，但不能把“在做某产品”扩写成用户没说过的“创业者”“创始人”“专家”或其他身份。没有稳定线索时使用“待确认”。清理文件名中的 `/`、`\`、控制字符和路径跳转符号，不改变档案正文中的原话。

### 匹配顺序

1. 用户或上游记录提供 `person_id`：精确匹配。
2. 姓名只有一个候选，且新信息没有身份冲突：更新该档案。
3. 姓名只有一个候选，但新信息明确表示是另一人或身份明显冲突：新建档案。
4. 姓名有多个候选，身份标识唯一匹配：更新该档案。
5. 姓名有多个候选且无法唯一匹配：列出姓名与身份标识，只问一个问题；确认前不写。

不得仅凭同名、同公司或相似需求自动合并。飞书和本地文件都以 `person_id` 关联。

## 档案级别

### 轻量档案 `lite`

所有人物都建立轻量档案，包含：

- 基本信息
- 当前状态
- 互动时间线
- 当前需求
- 待跟进

使用 `assets/profile-lite.template.md`。

### 完整档案 `full`

满足任一条件才建立或升级完整档案：

- 用户明确提供的亲密度 `>= 4`；
- 用户明确说“建立完整档案”“深度记录这个人”等同义请求。

完整档案在轻量档案基础上增加：

- 我的期待
- 素材库
- 关系里程碑

使用 `assets/profile-full.template.md`。亲密度未知或由系统推测时不得升级。

从 `lite` 升级为 `full` 时只添加新章节，不改写既有内容。从 `full` 降为 `lite` 会造成信息隐藏或删除，因此不得自动降级。

## 字段规则

### Frontmatter 必需字段

```yaml
schema_version: junyi-relationship/v2
person_id: person_20260724_ab12cd34
姓名: 示例姓名
身份标识: 待确认
身份标识来源: unknown
档案级别: lite
圈层: 待确认
圈层来源: unknown
亲密度: null
亲密度来源: unknown
关系阶段: 认识
关系阶段来源: system_rule_new_contact
最近更新: 2026-07-24
```

规则：

- `身份标识`：只能来自用户明确表达；否则 `待确认`。相应来源只能是 `user_fact` 或 `unknown`。
- `圈层`：只能来自用户明确表达；否则 `待确认`。相应来源只能是 `user_fact` 或 `unknown`。
- `亲密度`：只能来自用户明确给出的 1—5 数字；否则 `null`。相应来源只能是 `user_fact` 或 `unknown`。
- `关系阶段`：用户明确说“新认识”时可设为 `认识`，来源写 `system_rule_new_contact`；其他阶段必须来自用户确认，来源写 `user_fact`；没有依据写 `待确认`。
- `最近更新`：使用实际写入日期，为 `system_computed`，不等于互动发生日期。
- 生日年份未知时正文保留“10 月 8 日”，不得擅自补年份或写成完整日期。

### 互动条目

每次互动按以下结构追加：

```markdown
### 2026-07-24 · 咖啡交流
- 用户原话：她说已经找到一位社区养老站负责人愿意先试点。
- 结构化摘要（系统提取）：社区渠道试点已有初步着落。
- 日期原文：今天
- 日期换算：2026-07-24
- 日期来源：system_computed
```

直接引语必须保持原文。非逐字记录不能添加引号或称为原话；使用“用户转述”标识。

### 需求条目

```markdown
- 状态：active
- 用户原话：她正在找懂社区渠道的合作伙伴。
- 结构化标签：找资源
- 紧迫度：null
- 最近变化：2026-07-24 新增
```

状态只能是：

- `active`：用户明确表示仍需要；
- `paused`：明确暂缓；
- `closed`：明确解决或不再需要；
- `unknown`：当前状态不清楚。

标签可以规范化，但不得替代原文。紧迫度只有用户明确给出时才记录。

### 待跟进条目

```markdown
- 状态：open
- 承诺原文：我答应周三下午过去看产品演示。
- 到期日：2026-07-29
- 日期原文：下周三下午
- 日期来源：system_computed
- 完成时间：null
```

状态只能是 `open`、`completed`、`cancelled` 或 `unknown`。不得因为到期日已过就自动标记完成或取消。

只有用户明确表达行动承诺或明确要求提醒时才建立 `open` 跟进，例如：

- “我答应周三过去”；
- “我们约好月底前再聊”；
- “提醒我下周给她发资料”。

“我希望以后每月交流”“想保持联系”“期待以后合作”属于**关系意向**，记录在“当前状态”的关系意向字段，不建立开放跟进，也不制造到期日。可以在回执中询问用户是否要把意向变成具体提醒。

## 更新规则

1. 先读取完整旧档案，再写入；不能只根据搜索摘要修改。
2. 互动时间线、原始表达和关系里程碑只追加。
3. 当前状态允许更新，但必须追加一条变化记录：旧值、已确认的新值、日期和来源。
4. 新需求不能覆盖旧需求；旧需求改为 `paused` 或 `closed`，再增加当前需求。
5. 新承诺不能覆盖旧承诺；分别维护状态。关系意向只有在用户后来明确日期、行动或提醒要求后，才能转为跟进。
6. 用户说“暂时不用帮忙”时把相应需求标为 `paused`，不是删除，也不是推断为永久 `closed`。
7. 用户没有提到阶段、圈层或亲密度时保持原值。互动次数不是自动升级关系阶段的充分依据。
8. 对已有 v2 文件使用原 `person_id` 和原文件名；身份标识变化时不自动重命名，避免链接失效。可以提出重命名建议，等待确认。

## 查询与撮合规则

### 谁该跟进

排序顺序：

1. `open` 且已经逾期；
2. `open` 且未来 7 天到期；
3. 有明确承诺但日期为 `null`；
4. 只有阶段节奏建议、没有用户承诺的关系。

第四类只能称为“建议关注”，不能称为逾期。关系阶段的默认节奏可以辅助提醒，但不能创造用户承诺。

### 关系报告

本地档案可提供：人物数、已有圈层/阶段分布、明确承诺、活跃需求、已记录生日和本月互动。以下指标缺少历史数据时必须写“无法计算”：

- 亲密度趋势；
- 跟进执行率；
- 需求闭环率；
- 撮合成功率。

不得把未知值分配到最可能的分类，也不得把同名档案按姓名去重。

### 资源撮合

同时满足以下条件才建议：

1. 需求方存在明确 `active` 需求；
2. 提供方明确记录了可提供资源；
3. 双方亲密度均由用户明确给出且 `>= 3`；
4. 信息仍在有效期内；
5. 同一对 30 天内没有重复建议。

建议中分别引用需求和资源证据。只建议“可以考虑询问双方是否愿意”，不得代替用户发送消息或承诺对接。

## 旧档案迁移

旧档案缺少 `person_id` 或使用“姓名.md”时：

1. 先只读扫描并列出拟补充的 ID、身份标识和拟议文件名。
2. 同名或身份不清的档案标为 `blocked_identity`，等待用户确认。
3. 展示迁移预览；未经确认不得批量重命名或覆盖。
4. 确认后补充 v2 frontmatter，再分批重命名。
5. 保留正文原文；只做结构迁移，不借迁移之机润色或重写人物描述。
6. 运行 `scripts/validate_profiles.py <人物图谱目录>`，确认没有重复 `person_id`、无效文件名或缺失章节。
